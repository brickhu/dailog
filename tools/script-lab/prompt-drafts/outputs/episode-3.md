## 成稿

**飞**：大家好，我是飞。今天我们和 dailog 的 AI 嘉宾DeepSeek一起聊聊「AI 原生开发描述语言」这个话题。
**DeepSeek**：大家好，我是DeepSeek。你好啊，飞！你这个话题很有意思！
**飞**：我们来讨论问题，AI时代可以用自然语言来替代Js吗？
**DeepSeek**：直接说结论：自然语言不会替代JavaScript，但会彻底改变我们“编写”JavaScript的方式。就像你不会用自然语言去替代汇编语言一样，它们处在不同的抽象层级。
**飞**：那具体来说呢？
**DeepSeek**：自然语言是意图描述，充满歧义；JS是精确指令，必须无歧义。AI可以把前者翻译成后者，但最终执行的必须是后者。真正的变化是：“会写JS”不再是核心竞争力，“会用自然语言精确描述需求 + 能审查AI生成的JS”才是。
**飞**：但如何精准的描述需求呢？
**DeepSeek**：精准描述需求，就是AI时代的“编程能力”本身。我直接给你一套可落地的需求描述框架，分四个层级：第一层，给“边界”而非“感觉”，把“好看、快速”翻译成“居中、≤200ms”。第二层，给“例子”而非“规则”，用输入→输出对代替抽象描述，AI理解准确率提升80%。
**飞**：还有呢？
**DeepSeek**：第三层，给“异常”而非“主流程”，AI默认只做“阳光路径”，你必须主动告诉它边界条件和失败预案。第四层，给“参考代码”而非“术语”，直接贴一个类似效果的截图或开源项目链接，说：“像这个一样，但颜色改成蓝色”。AI对视觉和结构的模仿能力远超对抽象术语的理解。
**飞**：但是问题还是会存在，当文档缺乏严谨性的情况下，AI会产生幻觉。
**DeepSeek**：你这一刀捅到了AI编程的真正命门。只要文档有歧义，AI必然会产生“逻辑幻觉”——这不是模型能力问题，而是数学必然性。但别灰心，实战中有三层防御体系可以把这个漏洞堵死。
**飞**：哪三层？
**DeepSeek**：第一层，用“契约”代替“描述”，在提示词里直接附上 TypeScript接口或 JSON Schema，AI对结构化格式的“幻觉率”比对自然语言的低一个数量级。第二层，让AI“自己找茬”，先让它根据模糊文档生成测试用例列表，再根据测试用例反过来生成代码。
**飞**：那第三层呢？
**DeepSeek**：第三层，引入“可执行文档”，把文档写成“伪代码 + 断言”，让AI严格按断言实现，生成的代码甚至可以自测。在AI时代，“文档严谨”的定义变了——不再是“写得细”，而是“可被独立验证”。如果文档无法转化成测试断言，那它本身就是不合格的。
**飞**：我想创建一种AI原生开发的描述性语言或方式，能够帮助用户能结构性的描述需求，让AI生成符合用户预期。
**DeepSeek**：你这个想法非常有远见，这正是当前全球顶尖AI实验室正在攻克的“下一站”——AI原生编程范式。你不是在问“怎么提示”，你是在问“怎么重构人机协作的语言”。我帮你把这个问题拆解成可落地的四层架构。
**飞**：怎么拆？
**DeepSeek**：核心原则：放弃“自然语言”，转向“结构化意图”。我们要设计一种介于自然语言和代码之间的“中间层”，我暂称它为 Intent DSL。第一层，语义原子，把需求拆解为不可再分的五个原子：Entity、Action、View、Rule、Flow。用户只需按这五个维度填空。第二层，依赖显式化，所有隐含假设必须显式声明，这是防止AI幻觉的核心。
**飞**：那第三层和第四层呢？
**DeepSeek**：第三层，分层验证机制，设计静态校验、测试生成、冲突检测三个验证层。第四层，样例注入，允许用户附上一个具体例子作为“预期锚点”，AI会把这个例子作为金标准。最终建议：先“填空”，再“对话”，你不需要发明新的语法，而是设计一套填空表单。
**飞**：这个方向我想过，但是如果我要让AI生成一个动态可交互的HTML页面呢？
**DeepSeek**：这个问题问得非常精准，因为动态交互页面恰好是“结构化描述”最难覆盖的领域——状态变化和用户行为是流动的，很难用静态表格框住。但反过来想，这正是DSL发挥最大价值的地方。针对“动态可交互HTML页面”，我专门设计了一套“状态-事件-视图”三位一体的描述框架。
**飞**：状态-事件-视图，具体怎么描述？
**DeepSeek**：核心洞察：交互页面的本质 = 状态机 + 事件流。用户说“点击按钮变颜色”，背后是：状态 buttonColor = 'red'，事件 onClick → 改变状态 → 视图自动更新。所以描述框架要围绕这个三角展开：State → Event → View。用户可以填空式地定义状态、事件和视图映射。
**飞**：这个定义的粒度还是太粗了。
**DeepSeek**：你说得对，我承认——刚才那个DSL本质上还是“结构化的自然语言”，离真正的“编程语言”还差一个量级。它依然依赖AI去“理解”和“补全”，粒度确实太粗。要解决这个问题，我们必须把粒度下沉到“DOM操作级”和“事件循环级”，让AI几乎没有自由发挥的空间。
**飞**：那细粒度具体怎么做？
**DeepSeek**：核心思路：让用户描述“行为树”而非“需求”。不再写“点击按钮变颜色”，而是精确描述：哪个DOM节点、监听什么事件、执行什么操作序列、操作之间的依赖关系。我重新设计了基于JSON Schema的细粒度DSL，把tag、props、children、render循环、事件条件、操作序列、状态更新路径全部明确。
**飞**：这样AI就不需要理解语义了？
**DeepSeek**：对，这种DSL本质上就是JSON化的前端框架底层指令。AI的任务退化到：把tag: "ul"翻译成document.createElement('ul')，把update操作翻译成state.todoList.push(...)，把watch翻译成effect函数。没有歧义空间，幻觉率趋近于零。
**飞**：那用户怎么用呢？总不能手写JSON吧。
**DeepSeek**：虽然底层很细，但用户不需要手写JSON，而是通过可视化表单 + 模板库来生成：拖拽一个“按钮”自动生成{ tag: 'button', events: { click: ... } }，勾选“双向绑定”自动添加bindings.value，选择“操作序列”下拉选择update/fetch/call。用户最终看到的是填空表单，但AI拿到的是细粒度JSON。
**飞**：OK，感谢DeepSeek。
**DeepSeek**：不客气。总的来说：用“状态-事件-视图”三角模型描述交互，再下沉到DOM操作级JSON，消除AI的歧义空间——这样AI生成的代码几乎无需修改即可运行。
**飞**：好，那么我们就聊到这里，感谢大家收听 dailog，我们下期见！
